Automata · Colonel Blotto

첨부 개발설계서 v10과 참조 엔진을 바탕으로 만든 행사 운영용 웹 앱입니다. 병사 101명을 5개 전선에 배치하며, 참가자 화면·TV 스코어보드·명예의 전당·운영 콘솔을 하나의 서버에서 제공합니다.

배포 상태: 사용자가 생성한 Vercel 배포의 2026-10-22 실행 로그에서 ModuleNotFoundError: No module named 'server'를 확인했습니다. 이 수정본은 시작 파일의 Python 검색 경로와 server/** 배포 포함 설정을 보완합니다. 전체 폴더를 GitHub에 올린 뒤 새 배포에서 /healthz와 화면을 확인해야 하며, 실제 클라우드 동작 확인은 아직 남아 있습니다.

검증 상태: 기능 테스트 51개와 참조 엔진 20,000쌍 대조를 통과했습니다. 조회 최적화 후 대표 풀 1,700개·30건 동시 제출은 오류 0건, 로컬 p95 약 0.83초로 설계서의 500ms 목표에 미달합니다. 실제 Vercel/PostgreSQL·현장 인수시험은 남아 있습니다. 상세: docs/VERIFICATION.md.

1. 구성과 주소

주소 용도
/ 참가자 로그인, 게임 시작
/play 병사 배분
/result 제출 결과·간식 선택·수령
/board TV용 현재 순위·순환·남은 간식
/hall 일별·종합 확정 명예의 전당
/admin 운영진 콘솔
/healthz 서버·DB 연결·한국 시각 확인

프론트엔드는 외부 CDN 없이 실행되는 HTML/CSS/JavaScript 모듈이고, 서버는 FastAPI + NumPy입니다. 프레임워크는 설계서의 권장 기술에서 경량 구성으로 바꾸었지만 게임 규칙은 서버에서 강제합니다. Vercel에서는 PostgreSQL을, 노트북에서는 SQLite를 사용합니다.

Vercel 화면 + Vercel Python API → Neon PostgreSQL

Vercel은 화면뿐 아니라 Python API도 실행할 수 있습니다. 다만 함수의 로컬 파일이나 메모리를 영구 DB로 사용할 수 없습니다. 그래서 Vercel에서 DATABASE_URL이 없으면 제출을 거절하며, 임시 SQLite로 조용히 대체하지 않습니다. 모든 서버 인스턴스가 같은 DB를 보고 제출·간식 예약을 트랜잭션으로 처리합니다.

2. 가장 쉬운 배포: GitHub + Vercel + Neon

A. 소스 올리기

  1. ZIP을 풀어 blotto 폴더를 엽니다. app.py, requirements.txt, vercel.json, public, server가 있는 위치가 프로젝트 루트입니다.
  2. GitHub에서 개인 계정 소유의 비공개 저장소를 만듭니다. Vercel Hobby의 Git 조직 저장소 연결 제한을 피할 수 있습니다. 이미 적합한 저장소가 있으면 사용해도 됩니다.
  3. 프로젝트 루트의 파일과 폴더를 업로드하거나 Git으로 push합니다. ZIP 자체만 업로드하면 실행되지 않습니다.
  4. 실제 .env, DB, 백업, PIN을 저장소에 올리지 않습니다. .env.example은 빈 설정 예시이므로 포함해도 됩니다.

B. 무료 PostgreSQL 만들기

  1. Neon에 가입하고 Free 프로젝트를 만듭니다. 유료 업그레이드를 선택할 필요는 없습니다.
  2. Vercel 함수의 기본 설정은 Tokyo (hnd1)입니다. Neon에서 Tokyo를 선택할 수 있으면 같은 지역으로 맞춥니다. 다른 지역을 사용한다면 vercel.json의 region도 가까운 지역으로 바꾸세요.
  3. 프로젝트의 Connect 화면에서 데이터베이스와 역할을 선택하고 Connection pooling을 켭니다.
  4. postgresql://... 형식의 연결 문자열을 복사합니다. 보통 호스트에 -pooler가 들어가며 SSL 옵션이 붙어 있습니다. 이것이 DATABASE_URL 값입니다. 값 전체는 비밀번호이므로 채팅이나 저장소에 붙여넣지 마세요.
  5. 백업용으로 pooling을 끈 직접 연결 문자열도 따로 보관합니다. 운영 노트북의 DATABASE_URL_UNPOOLED에만 설정하면 됩니다.

Vercel의 Storage/Marketplace에서 Neon을 연결하는 방식도 가능합니다. 이 경우 자동으로 추가된 환경 변수 중 pooled PostgreSQL URL을 이 앱이 읽는 DATABASE_URL 이름으로 지정하세요. 비슷한 이름의 변수만 있고 DATABASE_URL이 없으면 앱이 DB를 사용하지 못합니다.

C. Vercel 프로젝트 가져오기

  1. Vercel에서 Add New → Project → Import Git Repository를 선택합니다.
  2. 위 저장소를 선택합니다. 프로젝트 생성 권한이 있는 개인 계정 또는 팀을 선택하세요. 이번 자동 배포 시도는 연결된 팀의 생성 권한 부족으로 실패했습니다.
  3. Framework Preset: FastAPI로 설정합니다. 소스에 포함된 vercel.json도 같은 값을 지정합니다.
  4. Root Directory는 app.py가 있는 폴더입니다. 저장소 최상위에 코드 파일을 올렸다면 기본값, 저장소 안에 blotto/ 폴더째 올렸다면 blotto입니다.
  5. Build Command / Output Directory / Install Command는 기본값을 사용합니다. 프론트엔드 npm build는 필요 없습니다. requirements.txt로 Python 의존성을 설치합니다.
  6. 아래 환경 변수를 Production에 넣습니다. Preview에는 별도 테스트 DB를 사용하세요.
변수 필수 여부 넣을 값
DATABASE_URL Vercel 필수 Neon의 pooled PostgreSQL URL 전체
ADMIN_PIN 필수 운영진만 아는 16자 이상 긴 비밀번호
PUBLIC_BASE_URL 배포 후 권장 실제 고정 주소, 예: https://프로젝트명.vercel.app (끝 / 없이)
PRIVACY_CONTACT 운영 전 설정 개인정보 담당자·연락 경로. 로그인 처리 안내에 표시됨

ADMIN_PIN이라는 이름이지만 4자리 PIN이 아니라 긴 비밀번호를 사용합니다. 앱에 기본 관리자 암호는 들어 있지 않습니다. DB_PATH는 Vercel에서 설정하지 않습니다. VERCEL은 플랫폼이 자동 설정하므로 직접 입력할 필요 없습니다.

  1. Deploy를 누릅니다. 처음에는 Python 패키지 설치 때문에 시간이 걸릴 수 있습니다.
  2. 완료 후 고정 Production 주소를 PUBLIC_BASE_URL로 설정하고 Redeploy합니다. 환경 변수 변경은 기존 배포에 자동 반영되지 않으므로 재배포가 필요합니다.
  3. 참가자에게는 매 배포마다 달라지는 Preview URL 대신 고정 Production 주소를 안내합니다.
  4. 실제 참가자 폰의 시크릿 창에서도 주소가 열리는지 확인합니다. Vercel 계정 로그인을 요구한다면 프로젝트의 Deployment Protection 설정을 확인해 행사 Production URL이 참가자에게 공개되도록 설정합니다. /admin은 앱 자체의 관리자 로그인으로 보호됩니다.

D. 서버가 정상인지 확인

https://실제주소/healthz를 열어 ok: true, db: "ok"와 한국 시각을 확인합니다. 이 확인만으로 행사 준비가 끝난 것은 아닙니다. /admin에서 재고·시드·운영일·임계값을 설정해야 합니다.

API 요청이 첫 실행될 때 테이블을 자동 생성합니다. 새 Neon 프로젝트에 SQL을 손으로 붙여넣을 필요가 없습니다. 임의의 기존 데이터베이스와 공유하지 말고 이 앱 전용 DB를 사용하세요.

E. No module named 'server'가 나타날 때

이 오류는 DB 연결 이전에 Python이 프로젝트의 server 패키지를 찾지 못했다는 뜻입니다. 로그만으로는 GitHub 업로드 누락, 배포 파일 누락, Python 검색 경로 문제 중 어느 것인지 확정할 수 없습니다.

  1. 이 수정본 ZIP을 새 폴더에 풀고, 안쪽 blotto 폴더를 엽니다.
  2. GitHub의 기존 app.py가 보이는 위치에서 Add file → Upload files를 누릅니다.
  3. 탐색기의 blotto 안에 있는 파일과 폴더 모두를 업로드 영역으로 끌어놓고 커밋합니다. server와 public 폴더도 반드시 포함합니다. ZIP 파일 자체나 바깥 blotto 폴더를 올리지 마세요.
  4. GitHub에서 app.py 옆에 server와 public 폴더가 있는지 확인합니다. server 안에는 __init__.py, app.py, db.py, engine.py, service.py가 있어야 합니다.
  5. Vercel의 새 배포가 방금 커밋을 사용했는지 확인합니다. 자동 배포가 시작되지 않으면 최신 커밋으로 배포합니다. 과거 커밋의 Redeploy는 수정 내용을 반영하지 않습니다.
  6. Production 주소의 /healthz에서 ok: true, db: "ok"를 확인하고 /, /play, /admin 화면을 확인합니다. db: "unavailable"이라면 서버를 불러오는 단계는 통과했으며, 다음으로 Production의 DATABASE_URL을 확인해야 합니다.

수정 파일: app.py(프로젝트 경로를 Python 검색 경로에 추가), vercel.json(server/** 포함), server/__init__.py(패키지 설명 추가). server는 외부 설치 라이브러리가 아니라 이 프로젝트에 포함된 코드입니다.

3. 배포 직후 운영 준비 순서

  1. /admin에서 ADMIN_PIN으로 로그인합니다.
  2. 운영일/설정에서 날짜와 운영시간을 확인합니다. 기본은 한국 시각 2026-10-30, 10-31, 11-01이며, 매일 10:00–13:00 / 14:00–17:00입니다. 달력이 아니라 관리자가 선택한 운영일 기준으로 하루 3회가 계산되며, 선택된 날짜·시간도 제출 시 확인합니다.
  3. 재고에서 실제 마이쮸·참깨 크래커·에이스 수량을 각각 입력합니다. 두 고급 상품의 개별 수량은 첨부 자료에 없으므로 임의로 나누지 않았습니다. 실제 수량 입력 전에는 고급 간식을 발급할 수 없습니다.
  4. 누적 상한은 설계서대로 마이쮸 188 / 338 / 450, 고급 합계 40 / 72 / 95입니다. 상한과 실물 재고는 서로 다른 값입니다. 실물 재고는 수령 시 줄고, 상한 카운터는 미수령 예약도 포함합니다.
  5. 시드에서 부원들이 직접 만든 전략을 최소 50개 입력합니다. 화면 입력, JSON 가져오기, CSV 가져오기를 지원합니다. 자동 시드 생성 기능은 없습니다. 가져오기는 추가 동작이므로 같은 파일을 반복 가져오지 마세요.
  6. 임계값에서 추천값을 확인하고 운영진이 승인한 값을 적용합니다. 7200은 승률 72.00%입니다. 1일차 추천값은 시드 풀의 참고값이므로 계획서의 별도 사전 보정 판단을 대신하지 않습니다.
  7. 개장합니다. 시드 50개, 임계값 적용, 유효한 날짜·시간·재고가 갖춰져야 정상 진행됩니다. 임계값은 하루에 한 번, 첫 개장 전에만 적용할 수 있습니다.
  8. TV에서 /board를 열어 전체화면으로 표시합니다. QR은 운영 콘솔에서 내려받습니다.

리허설은 Production과 다른 Neon 프로젝트/DB 또는 로컬 data/dress.db에서 하세요. 개장한 운영 DB에서는 RESET을 허용하지 않습니다. 행사 데이터를 지우고 다시 시작하는 버튼이 필요해지는 상황을 피하기 위한 제한입니다.

4. 참가와 간식 지급 흐름

재학생은 학번·이름·닉네임, 외부인은 닉네임과 동의로 시작합니다. 재학생은 다른 기기에서 같은 학번·이름으로 접속해도 횟수가 합산됩니다. 학번·이름이 본인 인증 수단은 아니라는 원래 설계의 한계는 그대로입니다. 외부인은 브라우저 쿠키를 삭제하거나 다른 기기를 쓰면 같은 사람임을 판별할 수 없습니다.

101명 배분을 제출하면, 누적 풀에서 본인의 모든 이전 제출을 뺀 상대들과 대결합니다. 같은 요청을 네트워크 오류 후 재전송해도 횟수와 재고는 한 번만 처리됩니다. 일일 첫 제출에만 간식을 판정하며, 2·3회차는 순위 경쟁용입니다.

TOP_CHOICE는 마이쮸·참깨·에이스 중 하나로 참가 간식을 대체합니다. 추가 지급이 아닙니다. 간식을 고르는 즉시 선택과 재고 예약이 서버에 저장되어 운영진의 미수령 목록에 표시됩니다. 선택 화면을 스태프에게 보여 주고 1초간 수령 버튼을 누릅니다. 성공 도장과 현재 움직이는 시계가 나타난 뒤 실제 간식을 지급합니다. 서버가 성공을 확인하기 전에 물품을 주지 마세요.

5. 설계서와 다르게 적용한 부분

원래 설계 이 구현
노트북 1대 + SQLite 기본 배포는 Vercel + PostgreSQL. 별도 로컬 모드에서 SQLite 지원
인터넷 없이 사용 로컬 모드는 가능. Vercel 모드는 참가자·TV·운영진 모두 인터넷 필요
외부 위탁 없음 클라우드 모드 안내에 Vercel·외부 DB 사용을 반영. 운영 전 담당자가 실제 계약·보관 정책을 확인해야 함
BEGIN IMMEDIATE로 쓰기 직렬화 SQLite는 동일, PostgreSQL은 트랜잭션 advisory lock 사용
메모리 순위 캐시 여러 함수 인스턴스가 공유하도록 DB에 캐시와 변경 버전 저장
장시간 SSE 짧은 SSE 연결을 자동 재연결하고 5초 폴링으로 복구
서버가 5분마다 로컬 백업 운영 노트북의 백업 스크립트 + Neon 복구 기능. Vercel 내부 파일 백업 없음
React + TypeScript 권장 빌드가 필요 없는 JavaScript 모듈. 외부 CDN 의존성 없음
제공 예정 로고 파일 첨부에 로고 원본이 없어 새 SVG 엠블럼 제작. 원본 확보 시 교체 가능

문서의 충돌은 최종 결정 사항(Q)을 우선했습니다. 개발설계서 4-4의 운영 중 임계값 상향 문구는 Q-5/R12와 충돌하므로 구현하지 않았습니다. T-07의 동시 제출 TOP_CHOICE 1 + BASIC 1은 EITHER 즉시 마감과 동시에 만족할 수 없습니다. 따라서 EITHER에서는 마지막 고급 예약 다음 요청이 CAP_REACHED, PREMIUM_SOFT에서는 고급 예약 1건 + BASIC 1건으로 검증합니다. 기본 설정은 최종 결정대로 EITHER입니다.

마감 후 사유를 남긴 REOPEN은 자동 상한 마감을 잠시 무시할 수 있지만, 개별 간식 재고·예약 상한을 넘는 발급은 허용하지 않습니다. 수령과 기존 기록 조회는 마감 후에도 가능합니다.

6. 무료 사용 범위와 비용 확인

Vercel Hobby는 개인·비상업 용도의 무료 플랜이며 사용량 한도가 있습니다. Neon에도 Free 플랜이 있습니다. 무료 플랜을 선택하고 그 한도 내에서 운영하는 구성이지, 어떤 사용량에서도 무료를 보장하는 구성은 아닙니다. 실제 계정이 Pro 팀인지도 대시보드에서 확인하세요. 앱에는 결제나 유료 서비스 자동 생성 기능이 없습니다.

2026-10-22 공식 문서 확인 기준, Hobby 함수 최대 실행시간은 300초이며 이 프로젝트는 요청당 최대 60초로 제한합니다. Hobby Cron은 하루 한 번만 실행할 수 있어 5분 백업을 예약하지 않았습니다. Neon Free의 시점 복구 창은 최대 6시간입니다. 긴 SSE 연결과 잦은 폴링도 사용량에 포함되므로 행사 중 필요한 TV·운영 화면만 켜두고 Usage를 확인하세요.

약 530명 규모라도 실제 네트워크·콜드 스타트·DB 지역·동시 사용 수에 따라 응답시간이 달라집니다. 로컬 측정값을 Vercel p95 보장으로 해석하면 안 됩니다.

블로토 행사 운영·백업·복구 안내

이 문서는 완성된 앱을 운영하는 담당자를 위한 안내입니다. Vercel 프로젝트와 DB를 처음 만드는 절차는 저장소의 배포 안내를 먼저 보세요. 모든 행사 시각은 한국 시각(Asia/Seoul) 입니다.

1. 두 실행 방식의 차이

구분 Vercel + PostgreSQL 부스 노트북 + SQLite
참가 주소 배포된 HTTPS 주소 노트북의 로컬 IP와 포트
인터넷 참가 폰과 서버 통신에 필요 같은 로컬 네트워크 안에서는 불필요
영구 데이터 별도 PostgreSQL DB DB_PATH에 지정한 파일
서버 재시작 Vercel이 함수 실행을 관리 scripts/run.py가 Uvicorn 종료를 감지해 2초 후 재시작
전체 백업 운영 노트북에서 pg_dump 실행 SQLite 온라인 백업 API
기본 백업 주기 별도 백업 터미널을 켜면 5분 로컬 실행 스크립트에 포함, 5분
최근 백업 유지 48개 48개

Vercel에는 SQLite DB를 저장하지 않습니다. 함수의 로컬 파일은 영구 저장소가 아니므로 DATABASE_URL이 없으면 실제 게임 API가 설정 오류를 반환하도록 만들었습니다. 화면 파일만 보이는 것과 서버 설정이 끝난 것은 다릅니다.

Vercel Hobby의 예약 작업은 하루 한 번까지만 실행됩니다. 따라서 이 프로젝트에는 5분 간격 Vercel Cron을 넣지 않았습니다. DB 서비스의 복구 기능과 아래 운영 노트북 백업을 함께 사용합니다. 노트북 전원·인터넷·백업 터미널 중 하나라도 꺼지면 해당 로컬 백업은 실행되지 않습니다.

2. 로컬 실행: Windows

프로젝트 폴더를 연 PowerShell에서 실행합니다. Python 3.12 이상이 필요합니다.

py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
notepad .env

.env에서 다음 항목을 실제 값으로 정합니다.

# 공개하지 않을 16자 이상의 운영 비밀번호
ADMIN_PIN=여기에_직접_정한_긴_비밀번호
DB_PATH=data/rehearsal.db
PORT=8000
PRIVACY_CONTACT=Automata 운영 담당자에게 문의

로컬 SQLite로 실행할 때 DATABASE_URL과 DATABASE_URL_UNPOOLED는 비워 두세요. 실제 행사는 DB_PATH=data/blotto.db, 개발은 data/dev.db, 리허설은 data/rehearsal.db처럼 분리합니다. 환경 변수로 이미 설정한 값은 .env보다 우선합니다.

.\.venv\Scripts\python.exe scripts/run.py

브라우저에서 http://localhost:8000/healthz와 http://localhost:8000/admin을 엽니다. 스크립트가 켜져 있는 동안 서버가 예기치 않게 종료되면 자동으로 재실행합니다. 정상 종료는 감시 스크립트 창에서 Ctrl+C입니다. 창을 닫거나 노트북을 종료하면 서버를 계속 감시할 수 없습니다.

다른 폰에서는 노트북과 같은 네트워크에 연결한 뒤 http://노트북_IP:8000으로 접속합니다. ipconfig에서 IPv4 주소를 확인하고, Windows 방화벽에서 해당 네트워크에 Python/8000 포트를 허용합니다. 학교 네트워크에서 기기 간 통신을 막으면 직접 접속은 불가능하므로 Vercel 주소를 사용하거나 담당자에게 연결 설정을 확인하세요.

PowerShell 실행 정책이 허용하는 환경에서는 scripts/start-local.ps1도 같은 실행을 합니다. Python을 직접 실행하는 위 명령에는 PowerShell 스크립트 실행 정책 변경이 필요 없습니다.

python3 -m venv .venv

4. 개장 전 한 번 할 설정

  1. /admin에서 .env 또는 Vercel에 지정한 ADMIN_PIN으로 로그인합니다.
  2. 운영일을 선택하고 실제 행사 날짜·운영 구간을 확인합니다. 기본값은 2026년 10월 30일, 10월 31일, 11월 1일의 10:00–13:00 / 14:00–17:00입니다. 리허설은 첫 개장 전에 날짜와 구간을 바꿉니다.
  3. 시드는 사람이 작성한 전략 50개 이상을 입력하거나 JSON/CSV로 가져옵니다. 앱에는 시드 자동 생성 기능이 없습니다. 입력 예시는 docs/seed-import-example.csv가 제공된 경우 그 형식을 참고하고, 실제 부원들이 작성한 값으로 채웁니다.
  4. 재고 메뉴에서 실제 수량을 실사 입력합니다. 마이쮸 총량은 450, 참깨와 에이스를 합친 고급 총량은 95가 설계 기준입니다. 참깨·에이스별 실물 수량은 운영진이 직접 입력해야 합니다. 일별 상한과 실물 재고는 별개입니다.
  5. 첫날은 시드로 검토한 임계값을 입력합니다. 둘째·셋째 날은 누적 풀에서 계산한 추천값을 확인하고 적용할 수 있습니다. 임계값은 그 운영일 최초 개장 전 한 번만 적용할 수 있습니다. 이미 개장한 날을 마감하거나 일시정지해도 잠금은 풀리지 않습니다.
  6. 실제 사용할 폰과 TV에서 /, /board, /hall을 열고 연결을 확인합니다. 서버 시각, 간식 수량, 최소 시드 수를 확인한 뒤 개장합니다.
운영일 마이쮸 누적 상한 고급 누적 상한
1일차 188 40
2일차 338 72
3일차 450 95

상한은 그날만의 사용량이 아니라 행사 전체의 누적 사용량과 비교합니다. 전날 사용하지 않은 몫은 다음 날 누적 상한에 자연스럽게 포함됩니다. TOP_CHOICE 미수령권은 최악의 경우를 고려해 고급으로 예약되므로, 실물 고급 재고와 예약 수는 같지 않을 수 있습니다.

5. 매일 운영 순서

시각 운영자가 할 일
09:30 /healthz, DB 연결, 날짜·시각, 운영일, 실물 재고, 백업 최신 시각을 확인합니다. 첫 개장 전 임계값을 적용합니다.
10:00 개장합니다. 참가자는 닉네임으로 표시되고, 첫 제출에서만 간식을 판정합니다.
13:00 일시정지하고 현장 안내를 합니다.
14:00 재개합니다. 서버의 설정된 운영 구간과 실제 안내가 맞는지 확인합니다.
14:00·15:00 수령 현황과 실물 바구니를 비교하고 차이는 사유와 함께 실사 보정합니다.
17:00 마감 → 해당 일별 순위 확정 → CSV 내보내기 → 전체 백업 확인 → 별도 매체에 복사합니다. 3일차에는 종합 순위도 확정합니다.

간식은 스태프 앞에서 참가자가 1초 동안 눌러 수령 완료를 표시한 뒤 지급합니다. 움직이는 시계·수령 도장·코드를 함께 확인합니다. 두 번째 수령 요청은 거절됩니다. 폰을 빌려준 경우 다음 사람에게 넘기기 전에 ‘다른 사람으로 시작’을 누르세요.

CAP_REACHED는 EITHER 규칙에 따른 정상 마감입니다. 운영자가 사유를 입력해 재개방할 수 있지만, 재개방으로 개별 상품의 실물 재고나 누적 상한을 초과 지급할 수는 없습니다. 임계값을 바꿔 재고 문제를 해결하는 기능은 없습니다.

설계서 T-07의 ‘마지막 고급 예약에 동시 제출 두 건이면 TOP_CHOICE+BASIC’ 예시는 EITHER의 즉시 마감과 충돌합니다. 구현은 최종 결정 Q-2를 우선합니다. EITHER에서는 먼저 처리된 요청이 마지막 고급을 예약하면 후속 요청은 CAP_REACHED이며, PREMIUM_SOFT 또는 사유 있는 재개방에서는 고급 소진 후 BASIC 전환을 시험할 수 있습니다.

6. 전체 백업

SQLite

로컬 감시 스크립트는 5분마다 backup/blotto-날짜-시각.db와 같은 이름의 .json 검사 파일을 만듭니다. 최근 48개를 보관합니다. 온라인 백업 API를 사용하므로 운영 중 커밋된 WAL 변경도 포함됩니다. 생성한 백업은 PRAGMA integrity_check와 주요 표 존재 여부를 검사합니다.

즉시 한 번 백업하려면 다음과 같이 실행합니다.

.\.venv\Scripts\python.exe scripts/backup.py create

macOS/Linux에서는 실행 파일만 .venv/bin/python으로 바꾸면 됩니다.

Vercel PostgreSQL

운영 노트북에 DB 서버와 같은 주 버전 또는 더 최신인 PostgreSQL 클라이언트를 설치하고 pg_dump, pg_restore를 PATH에서 실행할 수 있게 합니다. 노트북의 비공개 .env에 DB 제공자에게서 받은 직접 연결 주소를 넣습니다.

DATABASE_URL_UNPOOLED=여기에_DB의_직접_연결_주소

앱은 pooled DATABASE_URL을 사용해도 되지만, 백업·복구는 -pooler가 없는 직접 연결 주소를 따로 사용합니다. 이 스크립트는 풀러 주소로 관리 작업을 실행하지 않습니다. 주소를 채팅, Git, 명령행 인수에 넣지 마세요. 스크립트는 비밀번호를 PGPASSWORD 환경 변수로만 자식 프로세스에 전달합니다.

.\.venv\Scripts\python.exe scripts/backup.py create --loop

성공 시 .dump와 .dump.json이 생성됩니다. pg_dump의 일관된 스냅샷을 사용하고 아카이브 목록을 검사하며, 최근 48개를 유지합니다. 오류가 나면 성공했다고 표시하지 않으며 다음 5분 주기에 다시 시도합니다. 최근 성공한 파일의 시각을 직접 확인하세요. 백업 실패나 노트북 중단 중에는 ‘최대 5분 유실’을 보장하지 않습니다.

DB 제공자의 시점 복구와 별도로, 하루가 끝나면 최신 백업 한 쌍을 암호화된 USB 또는 접근을 제한한 별도 저장소로 복사합니다. 이 스크립트는 자동 외부 업로드를 하지 않습니다. 전체 백업은 학번·이름·세션 정보가 들어 있는 민감한 파일입니다. 운영 콘솔의 익명화 내보내기는 전체 복구용 백업을 대체하지 않습니다.

7. 복구

복구는 현재 DB를 과거 시점으로 되돌립니다. 복구 이후 제출·수령 기록이 취소될 수 있으므로 실제 지급한 간식과 반드시 대조합니다.

  1. 운영 콘솔을 마감하고 참가 접속을 중단합니다. 로컬은 scripts/run.py 창에서 Ctrl+C, Vercel은 프로젝트 트래픽을 중단하거나 복구용 점검 배포로 전환해 DB를 사용하는 앱을 멈춥니다. 콘솔의 마감 버튼만으로 모든 DB 쓰기가 중단되는 것은 아닙니다.
  2. 복구할 .db 또는 .dump 파일과 같은 이름의 .json 검사 파일을 준비합니다. 두 파일은 한 쌍입니다.
  3. 환경 변수가 대상 DB를 가리키는지 확인한 뒤 아래 명령을 실행합니다. 프로젝트 폴더 기준 경로 또는 절대 경로를 쓸 수 있습니다.
.\.venv\Scripts\python.exe scripts/backup.py restore backup/blotto-실제파일명.db --server-stopped --confirm RESTORE

PostgreSQL은 파일 확장자를 .dump로 바꾸고 .env의 DATABASE_URL_UNPOOLED를 대상 DB의 직접 주소로 지정합니다. 가능하면 운영 DB에 덮어쓰기 전에 새 복구용 DB/브랜치에 복원해 먼저 확인하세요.

복구 도구는 체크섬·형식·DB 종류를 검사하고, 기존 DB가 있으면 backup/pre-restore에 복구 직전 백업을 남깁니다. 이 사전 백업은 일반 48개 정리 대상에서 분리됩니다. SQLite는 남은 WAL/SHM도 진단용으로 보존한 다음 복원하고, PostgreSQL은 단일 트랜잭션으로 복원해 중간 실패가 반쯤 적용되지 않게 합니다. 이 확인 절차가 다른 서버가 정말 멈췄는지 원격으로 보장하지는 않으므로 담당자가 먼저 서비스 중단을 확인해야 합니다.

  1. 서버를 시작하고 /healthz를 확인합니다.
  2. 제출 수, 운영일, 사용량·예약량, 상품별 실물 재고, 확정 순위를 복구 시점 기록과 대조합니다.
  3. 문제가 없으면 운영을 재개합니다. 복구 시점 이후 이미 지급한 간식은 재고 실사 보정과 수령 내역 정리가 필요할 수 있습니다.

응답시간과 실시간 갱신

초기 자동 부하 시험은 시드 1,700개 + 신규 참가자 30명에 동시에 제출했습니다. 오류와 재고 불일치는 없었으며, 당시 전체 테스트 실행에서 p95 692ms, 최대 695ms였습니다. 반복 측정은 약 0.7~0.8초 범위였습니다. 이는 많은 기존 순위 대상 참가자가 있는 상황보다 가벼운 조건입니다. 실제 행사 구성으로 교체한 최종 측정은 다음 단락을 참고하세요.

대표 구성의 최종 측정: 시드 50개 + 참가자 550명 × 제출 3회 = 1,700개 풀에서 신규 참가자 30명이 동시에 제출했습니다. 최초 측정 p95는 1,335.6ms였고, 제출 경로의 불필요한 참가자 JOIN·표시용 열과 SQLite 행 변환 비용을 줄인 뒤 전체 시험을 다시 실행했습니다. 최종 p95 833.3ms, 최대 842.7ms, 오류 0건이었습니다. 실행 환경에 따라 편차가 있으며, 여전히 설계 목표 p95 500ms에는 미달합니다. 제출 후 1,730개 전략의 캐시 점수·상대 수를 전체 재계산과 비교해 모두 일치했으며, 순위 대상 580명과 신규 BASIC 예약 30개도 정확했습니다. 격리된 시험 DB에서 기존 참가자의 과거 보상 발급은 생략했습니다. 이 로컬 SQLite/TestClient 수치는 실제 Vercel/PostgreSQL 성능을 보장하지 않습니다.

순위 엔진 단독으로 시드 50개와 3회 제출 참가자들을 섞은 2,100개 풀을 시험했을 때 전체 점수 재계산 약 77ms, 정확한 분수 순위 계산 약 4ms였습니다. 이 값은 API·네트워크·DB 접속 지연을 포함하지 않습니다.

SSE 생성기가 커밋된 변경을 반영하는 데 최종 시험 기준 약 1.57초 걸렸습니다. 이것은 서버 내부 생성기 시험이며 Vercel을 거친 전송 지연, 20개 연결의 30분 유지, 콜드 스타트 이후 재연결까지 보장하지 않습니다.

  2. 배포된 API의 콜드/웜 응답시간, 동시 30명과 풀 1,700/2,100 성능 측정. 현재 500ms 목표 미달을 해소하거나 운영진이 허용 지연을 명시적으로 조정해야 함.
  3. 휴대폰 15대 이상, 학교 Wi-Fi·모바일 데이터 접속, 네트워크 차단·새로고침·미수령 복원 확인.
  4. TV 5m 가독성, SSE 20개 화면 30분, 실제 길게 누르기 수령 확인.
  5. 운영진 2명이 개장·재고 실사·마감·확정·백업·복구를 직접 수행.
  6. 실제 데이터베이스 백업 복구와 개인정보·백업 파기 절차 확인.

최초 자동 프로젝트 생성 요청은 403 권한 오류로 거절되었고, 이후 사용자가 직접 만든 배포에서 패키지 로딩 오류를 확인했습니다. 수정본의 실제 클라우드 정상 동작은 새 배포 후 확인해야 합니다.
