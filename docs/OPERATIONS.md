# 블로토 행사 운영·백업·복구 안내

이 문서는 완성된 앱을 운영하는 담당자를 위한 안내입니다. Vercel 프로젝트와 DB를 처음 만드는 절차는 저장소의 배포 안내를 먼저 보세요. 모든 행사 시각은 **한국 시각(Asia/Seoul)** 입니다.

## 1. 두 실행 방식의 차이

| 구분 | Vercel + PostgreSQL | 부스 노트북 + SQLite |
|---|---|---|
| 참가 주소 | 배포된 HTTPS 주소 | 노트북의 로컬 IP와 포트 |
| 인터넷 | 참가 폰과 서버 통신 및 Google 인증에 필요 | 외부인 로컬 참여는 불필요. 학생 Google 인증은 인터넷 필요 |
| 영구 데이터 | 별도 PostgreSQL DB | `DB_PATH`에 지정한 파일 |
| 서버 재시작 | Vercel이 함수 실행을 관리 | `scripts/run.py`가 Uvicorn 종료를 감지해 2초 후 재시작 |
| 전체 백업 | 운영 노트북에서 `pg_dump` 실행 | SQLite 온라인 백업 API |
| 기본 백업 주기 | 별도 백업 터미널을 켜면 5분 | 로컬 실행 스크립트에 포함, 5분 |
| 최근 백업 유지 | 48개 | 48개 |

**Vercel에는 SQLite DB를 저장하지 않습니다.** 함수의 로컬 파일은 영구 저장소가 아니므로 `DATABASE_URL`이 없으면 실제 게임 API가 설정 오류를 반환하도록 만들었습니다. 화면 파일만 보이는 것과 서버 설정이 끝난 것은 다릅니다.

Vercel Hobby의 예약 작업은 하루 한 번까지만 실행됩니다. 따라서 이 프로젝트에는 5분 간격 Vercel Cron을 넣지 않았습니다. DB 서비스의 복구 기능과 아래 운영 노트북 백업을 함께 사용합니다. 노트북 전원·인터넷·백업 터미널 중 하나라도 꺼지면 해당 로컬 백업은 실행되지 않습니다.

## 2. 로컬 실행: Windows

프로젝트 폴더를 연 PowerShell에서 실행합니다. Python 3.12 이상이 필요합니다.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
notepad .env
```

`.env`에서 다음 항목을 실제 값으로 정합니다.

```dotenv
# 공개하지 않을 16자 이상의 운영 비밀번호
ADMIN_PIN=여기에_직접_정한_긴_비밀번호
DB_PATH=data/rehearsal.db
PORT=8000
PRIVACY_CONTACT=Automata 운영 담당자에게 문의
```

로컬 SQLite로 실행할 때 `DATABASE_URL`과 `DATABASE_URL_UNPOOLED`는 비워 두세요. 실제 행사는 `DB_PATH=data/blotto.db`, 개발은 `data/dev.db`, 리허설은 `data/rehearsal.db`처럼 분리합니다. 환경 변수로 이미 설정한 값은 `.env`보다 우선합니다.

```powershell
.\.venv\Scripts\python.exe scripts/run.py
```

브라우저에서 `http://localhost:8000/healthz`와 `http://localhost:8000/admin`을 엽니다. 스크립트가 켜져 있는 동안 서버가 예기치 않게 종료되면 자동으로 재실행합니다. **정상 종료는 감시 스크립트 창에서 Ctrl+C**입니다. 창을 닫거나 노트북을 종료하면 서버를 계속 감시할 수 없습니다.

외부인 모드의 로컬 시험은 다른 폰에서 노트북과 같은 네트워크에 연결한 뒤 `http://노트북_IP:8000`으로 접속할 수 있습니다. `ipconfig`에서 IPv4 주소를 확인하고 Windows 방화벽에서 해당 네트워크의 Python/8000 포트를 허용합니다. 학생 Google 로그인은 등록된 HTTPS 원본 또는 개발용 `localhost`에서 시험해야 하므로 실제 휴대폰에서는 등록된 Vercel 주소를 사용하세요. 학교 네트워크에서 기기 간 통신을 막으면 로컬 직접 접속도 불가능합니다.

PowerShell 실행 정책이 허용하는 환경에서는 `scripts/start-local.ps1`도 같은 실행을 합니다. Python을 직접 실행하는 위 명령에는 PowerShell 스크립트 실행 정책 변경이 필요 없습니다.

## 3. 로컬 실행: macOS/Linux

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
```

편집기로 `.env`를 수정한 뒤 실행합니다.

```bash
.venv/bin/python scripts/run.py
```

포트를 바꾸려면 `--port 8080`을 붙입니다. 서버의 자동 백업은 `--no-backup`으로만 끌 수 있으며, 행사 중에는 기본 설정을 권장합니다. 최초 `/healthz` 또는 게임 API 요청이 DB를 초기화하면 백업이 시작됩니다.

## 4. 개장 전 한 번 할 설정

1. `/admin`에서 `.env` 또는 Vercel에 지정한 `ADMIN_PIN`으로 로그인합니다.
2. 운영일을 선택하고 실제 행사 날짜·운영 구간을 확인합니다. 기본값은 2026년 10월 30일, 10월 31일, 11월 1일의 10:00–13:00 / 14:00–17:00입니다. 리허설은 첫 개장 전에 날짜와 구간을 바꿉니다.
3. **시드는 사람이 작성한 전략 50개 이상**을 입력하거나 JSON/CSV로 가져옵니다. 앱에는 시드 자동 생성 기능이 없습니다. 입력 예시는 `docs/seed-import-example.csv`가 제공된 경우 그 형식을 참고하고, 실제 부원들이 작성한 값으로 채웁니다.
4. 재고 메뉴에서 실제 수량을 실사 입력합니다. 마이쮸 총량은 450, 참깨와 에이스를 합친 고급 총량은 95가 설계 기준입니다. **참깨·에이스별 실물 수량은 운영진이 직접 입력**해야 합니다. 일별 상한과 실물 재고는 별개입니다.
5. 첫날은 시드로 검토한 임계값을 입력합니다. 둘째·셋째 날은 누적 풀에서 계산한 추천값을 확인하고 적용할 수 있습니다. 임계값은 **그 운영일 최초 개장 전 한 번만 적용**할 수 있습니다. 이미 개장한 날을 마감하거나 일시정지해도 잠금은 풀리지 않습니다.
6. 실제 사용할 폰과 TV에서 `/`, `/board`, `/hall`을 열고 연결을 확인합니다. 학생 학교 Google 로그인과 외부인 임시 참여를 시험합니다. 서버 시각, 간식 수량, 최소 시드 수를 확인한 뒤 **개장**합니다.

| 운영일 | 마이쮸 누적 상한 | 고급 누적 상한 |
|---|---:|---:|
| 1일차 | 188 | 40 |
| 2일차 | 338 | 72 |
| 3일차 | 450 | 95 |

상한은 그날만의 사용량이 아니라 행사 전체의 누적 사용량과 비교합니다. 전날 사용하지 않은 몫은 다음 날 누적 상한에 자연스럽게 포함됩니다. TOP_CHOICE 미수령권은 최악의 경우를 고려해 고급으로 예약되므로, 실물 고급 재고와 예약 수는 같지 않을 수 있습니다.

## 5. 매일 운영 순서

| 시각 | 운영자가 할 일 |
|---|---|
| 09:30 | `/healthz`, DB 연결, 날짜·시각, 운영일, 실물 재고, 백업 최신 시각을 확인합니다. 첫 개장 전 임계값을 적용합니다. |
| 10:00 | 개장합니다. 학생은 동의 후 학교 계정 이름, 외부인은 닉네임으로 표시되고 첫 제출에서만 간식을 판정합니다. |
| 13:00 | 일시정지하고 현장 안내를 합니다. |
| 14:00 | 재개합니다. 서버의 설정된 운영 구간과 실제 안내가 맞는지 확인합니다. |
| 14:00·15:00 | 수령 현황과 실물 바구니를 비교하고 차이는 사유와 함께 실사 보정합니다. |
| 17:00 | 마감 → 해당 일별 순위 확정 → CSV 내보내기 → 전체 백업 확인 → 별도 매체에 복사합니다. 3일차에는 종합 순위도 확정합니다. |

간식은 스태프 앞에서 참가자가 **1초 동안 눌러 수령 완료**를 표시한 뒤 지급합니다. 움직이는 시계·수령 도장·코드를 함께 확인합니다. 두 번째 수령 요청은 거절됩니다. 폰을 빌려준 경우 다음 사람에게 넘기기 전에 ‘다른 사람으로 시작’을 누르세요.

`CAP_REACHED`는 EITHER 규칙에 따른 정상 마감입니다. 운영자가 사유를 입력해 재개방할 수 있지만, 재개방으로 개별 상품의 실물 재고나 누적 상한을 초과 지급할 수는 없습니다. 임계값을 바꿔 재고 문제를 해결하는 기능은 없습니다.

설계서 T-07의 ‘마지막 고급 예약에 동시 제출 두 건이면 TOP_CHOICE+BASIC’ 예시는 EITHER의 즉시 마감과 충돌합니다. 구현은 최종 결정 Q-2를 우선합니다. EITHER에서는 먼저 처리된 요청이 마지막 고급을 예약하면 후속 요청은 CAP_REACHED이며, PREMIUM_SOFT 또는 사유 있는 재개방에서는 고급 소진 후 BASIC 전환을 시험할 수 있습니다.

## 6. 전체 백업

### SQLite

로컬 감시 스크립트는 5분마다 `backup/blotto-날짜-시각.db`와 같은 이름의 `.json` 검사 파일을 만듭니다. 최근 48개를 보관합니다. 온라인 백업 API를 사용하므로 운영 중 커밋된 WAL 변경도 포함됩니다. 생성한 백업은 `PRAGMA integrity_check`와 주요 표 존재 여부를 검사합니다.

즉시 한 번 백업하려면 다음과 같이 실행합니다.

```powershell
.\.venv\Scripts\python.exe scripts/backup.py create
```

macOS/Linux에서는 실행 파일만 `.venv/bin/python`으로 바꾸면 됩니다.

### Vercel PostgreSQL

운영 노트북에 **DB 서버와 같은 주 버전 또는 더 최신인 PostgreSQL 클라이언트**를 설치하고 `pg_dump`, `pg_restore`를 PATH에서 실행할 수 있게 합니다. 노트북의 비공개 `.env`에 DB 제공자에게서 받은 직접 연결 주소를 넣습니다.

```dotenv
DATABASE_URL_UNPOOLED=여기에_DB의_직접_연결_주소
```

앱은 pooled `DATABASE_URL`을 사용해도 되지만, 백업·복구는 `-pooler`가 없는 **직접 연결 주소**를 따로 사용합니다. 이 스크립트는 풀러 주소로 관리 작업을 실행하지 않습니다. 주소를 채팅, Git, 명령행 인수에 넣지 마세요. 스크립트는 비밀번호를 `PGPASSWORD` 환경 변수로만 자식 프로세스에 전달합니다.

```powershell
.\.venv\Scripts\python.exe scripts/backup.py create --loop
```

성공 시 `.dump`와 `.dump.json`이 생성됩니다. `pg_dump`의 일관된 스냅샷을 사용하고 아카이브 목록을 검사하며, 최근 48개를 유지합니다. 오류가 나면 성공했다고 표시하지 않으며 다음 5분 주기에 다시 시도합니다. **최근 성공한 파일의 시각을 직접 확인**하세요. 백업 실패나 노트북 중단 중에는 ‘최대 5분 유실’을 보장하지 않습니다.

DB 제공자의 시점 복구와 별도로, 하루가 끝나면 최신 백업 한 쌍을 암호화된 USB 또는 접근을 제한한 별도 저장소로 복사합니다. 이 스크립트는 자동 외부 업로드를 하지 않습니다. 전체 백업은 학번·이름·세션 정보가 들어 있는 민감한 파일입니다. 운영 콘솔의 익명화 내보내기는 전체 복구용 백업을 대체하지 않습니다.

## 7. 복구

**복구는 현재 DB를 과거 시점으로 되돌립니다. 복구 이후 제출·수령 기록이 취소될 수 있으므로 실제 지급한 간식과 반드시 대조합니다.**

1. 운영 콘솔을 마감하고 참가 접속을 중단합니다. 로컬은 `scripts/run.py` 창에서 Ctrl+C, Vercel은 프로젝트 트래픽을 중단하거나 복구용 점검 배포로 전환해 DB를 사용하는 앱을 멈춥니다. 콘솔의 마감 버튼만으로 모든 DB 쓰기가 중단되는 것은 아닙니다.
2. 복구할 `.db` 또는 `.dump` 파일과 **같은 이름의 `.json` 검사 파일**을 준비합니다. 두 파일은 한 쌍입니다.
3. 환경 변수가 대상 DB를 가리키는지 확인한 뒤 아래 명령을 실행합니다. 프로젝트 폴더 기준 경로 또는 절대 경로를 쓸 수 있습니다.

```powershell
.\.venv\Scripts\python.exe scripts/backup.py restore backup/blotto-실제파일명.db --server-stopped --confirm RESTORE
```

PostgreSQL은 파일 확장자를 `.dump`로 바꾸고 `.env`의 `DATABASE_URL_UNPOOLED`를 대상 DB의 직접 주소로 지정합니다. 가능하면 운영 DB에 덮어쓰기 전에 **새 복구용 DB/브랜치**에 복원해 먼저 확인하세요.

복구 도구는 체크섬·형식·DB 종류를 검사하고, 기존 DB가 있으면 `backup/pre-restore`에 복구 직전 백업을 남깁니다. 이 사전 백업은 일반 48개 정리 대상에서 분리됩니다. SQLite는 남은 WAL/SHM도 진단용으로 보존한 다음 복원하고, PostgreSQL은 단일 트랜잭션으로 복원해 중간 실패가 반쯤 적용되지 않게 합니다. 이 확인 절차가 **다른 서버가 정말 멈췄는지 원격으로 보장하지는 않으므로** 담당자가 먼저 서비스 중단을 확인해야 합니다.

4. 서버를 시작하고 `/healthz`를 확인합니다.
5. 제출 수, 운영일, 사용량·예약량, 상품별 실물 재고, 확정 순위를 복구 시점 기록과 대조합니다.
6. 문제가 없으면 운영을 재개합니다. 복구 시점 이후 이미 지급한 간식은 재고 실사 보정과 수령 내역 정리가 필요할 수 있습니다.

## 8. 현장 장애에 대한 짧은 대응

| 증상 | 먼저 확인할 것 | 조치 |
|---|---|---|
| 화면은 열리지만 게임이 안 됨 | `/healthz`, DB URL, 관리자 PIN, 날짜·운영 상태 | 설정 누락을 고치고 Vercel이면 환경 변수 변경 후 재배포 |
| `THRESHOLD_LOCKED` | 그 운영일에 이미 임계값 적용/개장을 했는지 | 정상 규칙입니다. 행사 데이터 초기화로 우회하지 마세요. |
| `POOL_TOO_SMALL` | 사람이 작성한 시드가 50개 이상인지 | 개장 전에 부족한 시드를 입력 |
| 합계 오류 | 5개 정수, 각각 0 이상, 합 101 | 입력 수정; 잘못된 입력은 횟수를 쓰지 않음 |
| 연결 중단 후 결과 모름 | 기존 화면의 다시 시도 기능 | 같은 요청 ID로 재시도; 새 참가자로 시작하지 않음 |
| 재고와 실물이 다름 | 미수령 예약·수령 완료·무효 처리 내역 | 원장에 사유를 남겨 실사 보정, DB 직접 수정 금지 |
| 자동 재시작이 안 됨 | 노트북 전원, 감시 스크립트 창, 포트 충돌 | 감시 스크립트를 다시 실행; 코드 오류면 개발진 연락 |
| Vercel 비용/한도 경고 | Vercel Usage, DB 사용량 | 한도를 확인하고 접속량·SSE 장시간 연결 운영을 조정; 무료 무제한을 가정하지 않음 |

서버와 폰의 시각은 서로 다를 수 있습니다. 판정 기준은 서버의 한국 시각이며, 운영 구간 밖에서는 개장 상태라도 제출이 제한됩니다. PC 절전과 자동 재부팅을 끄고 전원을 연결합니다.

## 9. 행사 종료 후 개인정보 정리

설계 기준은 행사 종료 후 7일 이내 파기입니다. 이번 기본 일정이 2026년 11월 1일 종료라면 **11월 8일 이내**에 정리를 완료합니다.

1. 운영을 완전히 마감하고 필요한 익명 통계만 내보냅니다.
2. 운영 콘솔의 개인정보 파기를 실행합니다. 확인 입력 `PURGE`와 사유가 필요하며 되돌릴 수 없습니다.
3. 운영 노트북의 `backup/`, `backup/pre-restore/`, 따로 복사한 DB·CSV·USB·드라이브 사본을 정리합니다. 백업 루프도 중지합니다.
4. DB 제공자의 복구 이력, 테스트 브랜치, 스냅샷에도 이전 개인정보가 남을 수 있으므로 보존 설정과 삭제 절차를 확인합니다. 앱 파기 버튼은 외부 백업까지 삭제하지 않습니다.
5. 개인정보가 포함된 이전 백업을 이후에 복원하지 않습니다. 파기 완료와 사본 정리를 운영진이 확인합니다.

## 10. 현장 인수에서 남은 확인

자동 테스트와 별개로, 행사 장소에서 15대 이상 실기기 접속, 30대 동시 제출, 실제 네트워크에서 지연 시간, 30분 TV 연결, 강제 종료·복구, 5m 거리 TV 가독성, 스태프의 실제 수령 절차를 확인해야 합니다. 클라우드 DB의 거리와 무료 DB의 절전 복귀 시간에 따라 실제 응답 속도가 달라질 수 있습니다.
