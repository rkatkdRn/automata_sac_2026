### Vercel 패키지 로딩 보완 · 2026-10-22

사용자가 제공한 배포 로그에서 `app.py`의 `from server.app import create_app`가 `ModuleNotFoundError`로 실패한 것을 확인했습니다. 정확히 어느 단계에서 패키지나 검색 경로가 누락됐는지는 원격 배포 파일에 접근하지 못해 확인되지 않았습니다.

시작 파일에 프로젝트 절대 경로를 추가하고, `vercel.json`에 `includeFiles: "server/**"`를 지정했습니다. 다른 작업 디렉터리에서 프로젝트 경로 없이 파일 로더로 앱을 불러오는 검사를 통과했습니다. `VERCEL=1`, `DATABASE_URL` 미설정 상태에서도 앱이 초기화되고 `/healthz`가 의도한 HTTP 503과 `db: "unavailable"`을 응답했습니다. 이것은 로컬 재현 시험이며 실제 Vercel에서 수정 적용이 완료됐다는 의미는 아닙니다.

## 응답시간과 실시간 갱신

초기 자동 부하 시험은 **시드 1,700개 + 신규 참가자 30명**에 동시에 제출했습니다. 오류와 재고 불일치는 없었으며, 당시 전체 테스트 실행에서 p95 **692ms**, 최대 **695ms**였습니다. 반복 측정은 약 0.7~0.8초 범위였습니다. 이는 많은 기존 순위 대상 참가자가 있는 상황보다 가벼운 조건입니다. 실제 행사 구성으로 교체한 최종 측정은 다음 단락을 참고하세요.

**대표 구성의 최종 측정:** 시드 50개 + 참가자 550명 × 제출 3회 = 1,700개 풀에서 신규 참가자 30명이 동시에 제출했습니다. 최초 측정 p95는 1,335.6ms였고, 제출 경로의 불필요한 참가자 JOIN·표시용 열과 SQLite 행 변환 비용을 줄인 뒤 전체 시험을 다시 실행했습니다. 최종 p95 **833.3ms**, 최대 **842.7ms**, 오류 **0건**이었습니다. 실행 환경에 따라 편차가 있으며, 여전히 설계 목표 **p95 500ms에는 미달**합니다. 제출 후 1,730개 전략의 캐시 점수·상대 수를 전체 재계산과 비교해 모두 일치했으며, 순위 대상 580명과 신규 BASIC 예약 30개도 정확했습니다. 격리된 시험 DB에서 기존 참가자의 과거 보상 발급은 생략했습니다. 이 로컬 SQLite/TestClient 수치는 실제 Vercel/PostgreSQL 성능을 보장하지 않습니다.

순위 엔진 단독으로 시드 50개와 3회 제출 참가자들을 섞은 2,100개 풀을 시험했을 때 전체 점수 재계산 약 77ms, 정확한 분수 순위 계산 약 4ms였습니다. 이 값은 API·네트워크·DB 접속 지연을 포함하지 않습니다.

SSE 생성기가 커밋된 변경을 반영하는 데 최종 시험 기준 약 **1.57초** 걸렸습니다. 이것은 서버 내부 생성기 시험이며 Vercel을 거친 전송 지연, 20개 연결의 30분 유지, 콜드 스타트 이후 재연결까지 보장하지 않습니다.

## 화면 검증

JavaScript 구문 검사와 정적 자산 경로 검사를 통과했습니다. 참가자·운영 콘솔의 API 응답 계약을 실제 FastAPI 결과와 대조했습니다. 주요 관리자 동작도 격리 DB의 API로 순서대로 실행했습니다.

제공된 브라우저 미리보기 환경에서는 Python 실행 파일을 사용할 수 없어 화면과 Python 서버의 브라우저 통합 시험을 완료하지 못했습니다. 별도로 **실제 서버 GET 응답을 저장한 화면 검수용 사본**을 브라우저에서 확인했습니다. 이 사본은 배포물에 포함하지 않습니다.

- 360×640 iframe에서 병력 입력과 제출 버튼이 스크롤 없이 보임.
- 합계 100일 때 제출 비활성화와 “병사 1명이 더 필요해요” 표시 확인.
- 합계 101 복원 후 첫 제출 확인창 표시 확인.
